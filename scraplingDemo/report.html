三级降级策略

大多数站点应该在第一层就结束，浏览器是最后手段而不是默认手段

L1

Fetcher

0.1 ~ 1 秒

curl_cffi + Chrome TLS 指纹 + HTTP/3，不启动浏览器。大量 WAF 只卡指纹，换掉指纹就通。

L2

StealthyFetcher

约 9 ~ 11 秒

隐身浏览器 + 指纹伪装，可解 Cloudflare 人机校验。应对 JS 安全检测页这类必须在真实浏览器里跑一遍的站点。

L3

DynamicFetcher

数秒 ~ 数十秒

标准 Playwright / Chrome，完整执行 JS。本次实测未触发，作为 SPA 兜底保留。

URL→L1 指纹伪装→ 未过 →L2 隐身浏览器→ 未过 →L3 标准浏览器 任一层达标即停止

踩坑记录

只用长度判成败会得到假的 4/4

base64 内嵌图片会把正文长度虚高十倍

36氪 的拦截页里正文其实只有一句「正在进行安全检测」。但直接取 page.markdown() 的长度是 1,037 字符——其中绝大部分是内嵌 base64 图片的编码， 看起来像是抓到了内容。剥离 base64 与图片标记后，真实正文只剩 56 字符。

markdown 原始长度
1,037
剥离 base64 后
56
判定条件
长度达标 + 关键词命中

因此脚本里先做 clean_markdown() 清洗，再要求「正文字符数 ≥ 阈值」且 「期望关键词命中」两个条件同时成立，才算真正抓到正文。

接进 hot 管线的三条建议

替换点是 news_content_extract.py 里的那次 requests.get

1

不要全量升级到浏览器

L2 单篇 9~11 秒，是 HTTP 层的 50~100 倍。每 6 小时跑一次的定时管线扛不住全量浏览器抓取。 正确做法：默认只走 L1，仅对失败的源按需降级。

2

先修指纹，再谈浏览器

LINUX DO 老方案 403 / SSLError，换 L1 指纹伪装后 1.1 秒就拿到 3,508 字符，根本不需要浏览器。 这类只卡 TLS 指纹的站点是最划算的一档，应当优先用 L1 消化掉。

3

把静默失败变成显性告警

当前真正的问题不是抓取能力不够，而是失败无声无息。建议给正文提取加一条 「字符数低于阈值即记 ❌ 到 meta.json」，坏源会自己暴露出来。
